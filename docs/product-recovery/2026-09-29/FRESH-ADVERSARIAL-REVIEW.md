Date: 2026-10-01.
Method: assume the recovered contract is wrong and N alternatives are valid. Try to produce behavior/lifecycle/configuration/journey/architecture it cannot explain.

## Challenges

### A1 — DINOForge is just a warfare pack toolkit
Falsified by recovered user intent: framework-first and total-conversion breadth. Warfare remains a specimen/domain, not product identity.

### A2 — DINOForge should simply be BepInEx plugins
Commodity stack explains injection/patching but not the accepted declarative/composition/total-conversion/evidence product thesis. Keep BepInEx/Harmony substrate; do not rebuild it.

### A3 — Registry replacement means reload complete
Falsified by FactionSystem, BuildMenu, Aerial, projectile static config/material cache, active waves and existing entities. Contract now models registry vs materialized consumers.

### A4 — Every domain should hot-reload live
Not required. Contract allows lookup-on-demand, materialized reconcile, new-only and restart-required. This avoids inventing unsafe reconciliation.

### A5 — Total conversion requires arbitrary code, so declarative-first is wrong
Contract says declarative-first, not declarative-only. Extension/plugin pillar exists; custom code may be needed while common content remains typed/composable.

### A6 — One host/profile is enough forever
Only CVP projection. Mature contract has explicit host compatibility/support matrix and subject identity.

### A7 — Assets are outside mod-platform scope
Rejected for mature total-conversion journey: visuals/audio/assets can be necessary to create a substantially different game. Exact breadth/licensing remains a product decision.

### A8 — Existing game entities should always migrate on G2
No. Contract explicitly requires existing/new-object policy per materialized domain; restart is valid.

### A9 — Packs are source folders, not immutable artifacts
Insufficient for evidence/composition. Contract separates source from candidate/artifact/digest/effective generation.

### A10 — A successful command is sufficient evidence
Rejected by exact-subject and runtime-effect invariants.

### A11 — Skills/weapons/squads can count because schemas exist
Rejected by four-stage realization gate.

### A12 — GenerationStore is overengineering; reload can mutate global registries
Current reproduced stale removal/patch/conflict behavior plus materialized consumers makes a candidate/acceptance distinction necessary. Implementation form can change, but semantic generation/acceptance cannot disappear without another mechanism satisfying same invariants.
